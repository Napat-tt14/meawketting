# Business registration

Product Owner decision, 2026-10-02: account registration and Business setup are separate flows. Signup asks only for email/password, or Google/LINE. The first authenticated visit without a workspace goes to a three-step setup, then Home. Verified new users may create a store only after confirming its details. Identity and client claims never assign Business authority.

## Implemented

- `/business/register` and `/business/login`: shared responsive Thai auth design, two email/password fields, password visibility, Google/LINE entry, busy/error and email-confirmation states. No Business fields appear in signup. Short CSS entrance motion and native page/card transitions cover navigation, email confirmation and setup steps; reduced-motion users receive immediate state changes.
- `POST /api/auth/email/register` creates only a Supabase account. If confirmation is enabled, it returns a check-email state without granting a session or creating domain records. `POST /api/auth/email/login` verifies credentials. Both use bounded JSON, strict same-origin checks, existing Worker/provider rate limits and secure HttpOnly session cookies. Passwords and provider error text are never logged or returned.
- `/api/auth/line/start` selects Supabase `custom:line`; Google retains its existing route. OAuth and email confirmation use PKCE and `/api/auth/google/callback`. A shared server-side account lookup directs unlinked verified users to `/business/setup` and active linked members to `/business/home`; inactive linked accounts fail closed. Client-supplied return destinations are not accepted.
- `/business/setup`: information → enabled services → review and explicit Owner declaration. Back/edit preserve form values. First-Branch name defaults to `สาขาหลัก`; Branch name/contact email are optional disclosures. Creation happens only on the final submission, then a document navigation opens `/business/home`. Incomplete accounts return to setup on their next login; completed accounts skip it. Direct operational access by an unlinked account also redirects to setup without granting data access. Setup has no operational navigation or marketing footer.
- `/api/business/register` verifies the user server-side, validates bounded same-origin input, and atomically creates Person, Business, first Branch, Owner membership, selected service modules, closed initial weekly hours, identity link, confirmation receipt and audit event. No customer, guardian or passport authority is created.
- PostgreSQL migration `202609200004_business_registration.sql` adds the private receipt table. Per-account transaction locks and a canonical request hash make identical concurrent retries return one store; changed retries conflict. Existing linked accounts cannot self-promote through signup. Failed transactions leave no partial authority.
- Phone and optional email are contact information, not verified phone/email ownership or legal-business checks. The checkbox confirms the applicant's declaration. Opening hours must be configured before accepting bookings.
- No new database migration is required: the existing `auth_person_links`, membership and atomic `business_registrations` receipt already distinguish account-only and completed setup. Refresh before final submission restarts the small wizard; it creates no partial store. Identical final retries remain safe.

## External configuration required — not yet deployed

1. Apply migrations with `npm run db:migrate` using the staging administrator connection. Keep Worker database credentials server-side and authorize its runtime role for the new receipt table as part of the existing privilege review.
2. Enable Email/password in Supabase Auth, configure confirmation mail delivery and the password policy (the UI requires at least 8 characters), and test the real confirmation link. Keep the default confirmation URL/PKCE flow targeting `/api/auth/google/callback`. Confirmation can be completed in another browser followed by password login; automatic PKCE session exchange requires the original browser. Also enable Google and configure its client ID/secret there. Copy the Supabase callback shown in the dashboard into Google's authorized redirect URIs.
3. Create a **LINE Login** channel (web app), separate from any messaging channel. In Supabase Authentication → Sign In / Providers → Custom Providers, add identifier `custom:line`, type **OAuth2**, with the LINE channel ID and channel secret. Configure:
   - Authorization URL: `https://access.line.me/oauth2/v2.1/authorize`
   - Token URL: `https://api.line.me/oauth2/v2.1/token`
   - Userinfo URL: `https://api.line.me/oauth2/v2.1/userinfo`
   - Scopes: `openid profile`; enable PKCE and `email_optional`. Userinfo subject/name/picture are `sub`, `name`, `picture`.
   - Copy the callback URL displayed by Supabase into the LINE channel callback settings. Enable appropriate test users while the channel is developing. Do not put the LINE secret in frontend code or Cloudflare browser bindings.
4. Set Supabase Site URL to the staging origin and allow exactly `https://STAGING_HOST/api/auth/google/callback`. The callback name is retained for compatibility and serves both providers. Configure the Cloudflare values listed in [the runbook](./PRODUCTION_RUNBOOK.md); no source edits are required.
5. Test both real provider redirects, cancellation, expired sessions, logout, fresh signup, repeated submission, revoked membership and Branch isolation with synthetic target accounts. LINE web ID tokens can use HS256, so this integration uses custom OAuth2 with userinfo, not an assumed JWKS-only custom OIDC configuration.

Sources: [Supabase password authentication](https://supabase.com/docs/guides/auth/passwords), [Supabase server-side PKCE](https://supabase.com/docs/guides/auth/server-side/advanced-guide), [Supabase custom providers](https://supabase.com/docs/guides/auth/custom-oauth-providers), [LINE Login API](https://developers.line.biz/en/reference/line-login/), [LINE ID-token verification](https://developers.line.biz/en/docs/line-login/verify-id-token/).

Use the same login provider for returning access. This feature does not implement manual cross-provider account linking or merge stores by contact email. Account recovery/relink remains an operator-verified process described in the runbook. LINE Login is authentication only, not a LINE Mini App or Pet authority.

## Local login diagnostics — 2026-10-02

- `GET /api/business/register` returning 401 on a public signup/login page means there is no verified session yet. The UI checks this deliberately. It retains 401 and no-store/correlation headers but no longer emits `api-failure` for this specific GET; rejected writes and other authentication/permission/server errors remain logged.
- Static auth/setup routes have identifiable, bounded log labels instead of `/api/other`. Rate-limit grouping stays unchanged. OAuth start failures log only the provider, application error code and an allowlisted configuration reason; raw provider messages, credentials, URLs and query values are excluded.
- A 302 from an OAuth start route means a redirect, not proof of a completed login. Read-only checks against the current local configuration confirmed Google redirects through Supabase to `accounts.google.com` and `custom:line` to `access.line.me`. No credentials were entered and no user/Business was created. Final provider sign-in, email delivery and callback completion still need real-account validation.
- The ignored local `.dev.vars` currently specifies `http://localhost:3000`. Open the app using exactly the configured origin. Another hostname or port is rejected, with `error=origin-mismatch` and a matching safe log reason. Supabase must allow the corresponding `/api/auth/google/callback` URL; see [Supabase redirect configuration](https://supabase.com/docs/guides/auth/redirect-urls).
- An epoch-sized `compile` duration in Vinext beta development logs results from comparing Worker and Node clock origins. The development response wrapper keeps the measured compile/render durations and uses zero for the incompatible origin offset. This normalization is development-only; total request timing and production responses retain their existing behavior.
