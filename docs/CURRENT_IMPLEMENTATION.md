## BE1 identity / Business / Branch implementation — 2026-09-06

BE1 is implemented as a local Cloudflare Worker/Vinext application boundary backed by D1-compatible SQLite. At the BE1 checkpoint it added durable `Person`, `Business`, `Branch`, `BusinessMembership`, explicit membership-to-Branch access, Branch modules/hours and append-only audit metadata. Customer/Pet was deliberately deferred then and is now implemented by BE2 below; Booking was deferred then and is now implemented by BE3. Service execution, LINE, payment, media and Consumer backends remain later phases.

| Area | Current implementation |
|---|---|
| Architecture | Frozen React UI → typed same-origin client → `POST /api/be1` → application authorization/validation → repository → D1. UI code never receives a database binding. |
| Persistence | Drizzle-defined relational schema and reproducible generated migrations for eight BE1 tables. Local development uses the D1 `DB` binding; fixtures are explicit dev/test seed data only. Branch grants retain active/inactive lifecycle and audit timestamps rather than requiring destructive deletion. |
| Person | Canonical human identity with opaque ID, active/inactive status and audit timestamps. It is not linked to Customer, Guardian or LINE identity in BE1. |
| Business / Branch | Durable profile, contact, timezone, active state, Branch contact/address, enabled modules and seven-day operating hours. A Business has many Branches; historical rows are retained when a Branch becomes inactive. |
| Membership / roles | Active/inactive Business memberships use the narrow `OWNER`, `MANAGER`, `STAFF` vocabulary. Owner has Business-wide Branch/configuration access; Manager and Staff require explicit active Branch grants. This is a foundation, not a granular permission matrix. |
| Server authorization | Every operation resolves actor Person → active membership → active Business → role/action → target Branch access. Client Business/Branch IDs are selectors only; wrong Business, inaccessible Branch, inactive membership and spoofed IDs are denied server-side. |
| Audit / correlation | Important mutations write actor, membership, Business/Branch scope, request ID, correlation ID, target and bounded before/after metadata in the same D1 batch/guarded mutation. |
| Frontend migration | BF10 text profile and Branch configuration now read/write through the typed backend client and one in-memory compatibility cache. The active context key remains a harmless session display preference; authorized workspaces and Branch truth come from the server after hydration. Legacy browser Business/Branch values are ignored and not backfilled. |
| Authentication | An explicit header-based adapter exists only when the server is configured as `dev-test`. Production authentication provider and external identity linking are **NOT IMPLEMENTED**; a production-mode request fails closed. |

Database scope now includes **BE1 + BE2 + BE3**. Service operations, Consent/Intake, Inbox/LINE, Billing/Payment, Reports, media/R2 and Consumer/Guardian backend are **NOT IMPLEMENTED**. Cloudflare production deployment is **NOT IMPLEMENTED**. The remaining BF1–BF12 local operational fixtures are compatibility data for those excluded domains and reference stable BE2 Customer/Pet plus BE3 Booking IDs.

## BE2 Customer / Pet implementation — 2026-09-07

BE2 extends the BE1 actor, active membership, Business authorization, application/repository and D1 patterns. It moves Business Customer and Business-local Pet relationship truth out of browser storage without changing the frozen Customers UI or starting Guardian/Passport authority.

| Area | Current implementation |
|---|---|
| Architecture | Frozen Customer/Pet screens → typed BE2 client → `POST /api/be2` → BE2 application validation/authorization → repository → the same D1 binding. The browser never queries D1 directly. |
| Persistence | Migration `0002` adds `customers`, identity-only `pets`, `business_pet_profiles`, `customer_tags` and `customer_pet_relationships`. Composite Business foreign keys prevent cross-tenant links; lifecycle checks and query-shaped indexes cover directory, phone duplicate, Pet-name duplicate and relationship traversal. |
| Customer | Stable opaque ID, Business scope, display name, optional phone/email, Business-owned notes, ordered lightweight tags, active/inactive lifecycle and actor/time metadata. One Customer record is shared across every Branch of its Business. |
| Pet | A minimal global opaque Pet anchor plus a mutable Business-local profile with name, Cat/Dog species, source, Business notes and lifecycle. The frozen UI has no real breed, sex or birth fields, so BE2 does not invent them. Avatars remain deterministic presentation; no R2 or upload system exists. |
| Relationship | `customer_pet_relationships` is a lifecycle-aware many-to-many Business contact association. It means only “this Customer is a contact/relationship for this Pet in this Business”; it never means Guardian, legal owner, Passport authority, Consent or Access Grant. |
| Search / duplicate handling | Business-scoped server queries search Customer name, normalized phone digits and linked active Pet name with limit/offset. Exact phone and Pet name/species candidates produce a non-destructive warning; staff must explicitly continue to create a separate record. Inactive identities remain warning candidates. No merge engine exists. |
| Authorization / Cross-Branch | Every BE2 operation resolves actor Person → active membership → active Business → Business-scoped target. OWNER, MANAGER and STAFF reuse the current active-membership operational foundation; Branch grants cannot expose another Business and do not fragment a Business-wide Customer/Pet directory. Wrong Business, spoofed IDs, inactive membership and cross-tenant links fail server-side. |
| Frontend migration | `/business/customers`, Customer Detail, Add/Edit Customer, Add Pet, notes, tags and search use backend truth after hydration. An in-memory compatibility cache preserves existing synchronous selectors, avatars, quick actions and remaining local Booking/Inbox/Billing/operations references by stable BE2 ID. The legacy session Customer slice is ignored, kept empty on writes and never backfilled or dual-written. |
| Passport compatibility | `be2PassportCompatibility.ts` is explicitly **DEV PROTOTYPE / NON-AUTHORITATIVE READ MODEL ONLY** for frozen seeded connection/access presentation. No Guardian, ownership, Consent, QR, protected Passport snapshot or access-grant column/API was added. New Business-local Pets default to unlinked presentation. |
| Audit / fixtures | Important mutations write actor, membership, Business, target, request/correlation ID, timestamp and bounded before/after shape in the same D1 batch. Contact values, names, notes and tag labels are not copied into audit JSON. `seed-be2-dev.sql` deterministically preserves legacy Customer/Pet IDs for dev/test only and never ingests session storage. |

At its own checkpoint BE2 intentionally stopped before Booking persistence; BE3 now supersedes that one exclusion. BE2 still does not implement service operations, Guardian, Passport/Consent, LINE, Payment, media or deployment.

## BE3 Booking / Calendar / Resource implementation — 2026-09-07

BE3 extends the same BE1 actor/membership and BE2 Customer/Pet architecture. It makes Booking planning durable without changing the frozen Calendar design or merging planning status into Grooming Job, Hotel Stay or Daycare Attendance execution.

| Area | Current implementation |
|---|---|
| Architecture | Frozen Calendar/Home/Customer projections → typed BE3 client/cache → `POST /api/be3` → BE3 application validation/authorization → repository → the same D1 binding. Browser code never queries D1 or supplies trusted availability. |
| Persistence | Migration `0003` adds ten normalized tables: planning services and their required Resource kinds, Resources and service links, Resource availability windows, Bookings, Booking↔Pet links, Resource assignments, a write-time reservation ledger and aggregate commit markers. Composite Business/Branch foreign keys prevent cross-tenant Customer/Pet/Resource links; query-shaped indexes cover Branch/range, Customer/range, module/status/range and Resource overlap. |
| Booking models | One durable aggregate supports `appointment` Grooming start/end, exclusive-checkout `date-range` Hotel stays, and `day` Daycare records. A Booking stores stable Business, Branch, Customer, service and planning state; Pet and Resource associations are normalized. The existing multi-Pet contract is preserved and capacity units count linked Pets. Current Customer/Pet/service labels are composed at read time rather than copied as identity snapshots. |
| Resource foundation | BE3 persists only the schedulable projection needed for Booking: Groomer, grooming station, dryer, Hotel planning capacity and Daycare zone capacity, plus service eligibility, active state and planning availability windows. `compatibilityStaffId` is an opaque bridge to the frozen BF9 directory, not Person, Membership, Team or HR truth. Hotel room/zone execution assignments remain local for BE4. |
| Availability / conflicts | Server preview and every mutation evaluate active Branch, enabled module, service, active Customer/Pets, active Customer↔Pet relationships, time shape, required/eligible Resources, Branch hours, Resource/compatibility-staff windows, exact duplicate fingerprint, exclusive overlap and per-day multi-Pet capacity. Expected business conflicts return typed recovery data instead of a generic 500. |
| Concurrency | Availability preview is advisory. Create/update stages the Booking aggregate, Pet links, assignments, reservations, commit marker and bounded audit in one D1 `batch()`. SQLite/D1 writer serialization plus reservation `BEFORE INSERT` triggers make a competing exclusive/capacity write observe the winner and abort the losing batch. Updates additionally use `WHERE revision = ?` optimistic compare-and-swap and a write token so stale edits return `VERSION_CONFLICT`. No distributed lock or client-side lock is claimed. |
| Idempotency | Create requires a Business-scoped idempotency key and stores a SHA-256 hash of the normalized request. Same key/same request returns the prior Booking; same key/different request returns `IDEMPOTENCY_KEY_REUSED`; the unique Business/key index also resolves racing retries. Edit/reschedule/resource commands use expected revision rather than a general mutation idempotency key; cancelling an already-cancelled Booking replays the current record. |
| Queries | Business-authorized list supports optional Branch, Customer, date/time overlap range, module, status and Resource filters with limit/offset; get and Branch catalogue queries remain scoped. Day/Week/Month/Custom Calendar ranges, including 28/35/42-day layouts, query one logical Booking per aggregate. Hotel is not expanded into daily Booking rows. |
| Frontend migration | The Business shell hydrates the permitted Business Booking directory page-by-page and each accessible Branch catalogue into memory. Frozen synchronous selectors project authoritative BE3 views; Calendar commands, drag/drop, both-edge resize and cancel send server mutations and use returned records/conflicts. Home and Customer upcoming Booking data derive from the same cache. Legacy `sessionStorage.bookings` is ignored and written empty; there is no browser backfill or dual write. |
| Execution compatibility | After an authoritative BE3 success, a best-effort adapter updates still-local Grooming Job, Hotel Stay and Daycare Attendance compatibility projections by stable Booking/Customer/Pet IDs. That local write is not atomic with D1 and is not Booking truth; BE4 must replace it with durable execution commands. |
| Authorization / audit | Every query or command resolves active Person → active Membership → Business → permitted Branch → target Booking/Customer/Pet/Resource. Wrong Business/Branch, foreign identities, inactive membership/grant and spoofed targets fail server-side. Create, update/reschedule, Resource change and cancel write actor, membership, Business/Branch, target, request/correlation ID, timestamp and bounded structural before/after metadata without duplicating Customer contact or notes in audit JSON. |
| Time limitation | BE3 deliberately stores validated Branch-local ISO-like values and comparable “civil minute” integers. The BE1 IANA timezone is not yet used to convert appointments to UTC instants or resolve DST/offset changes. Current hours enforcement checks the start weekday and applies open/close times only to appointments; date-range/day per-day opening policy remains an open production rule. |

The BE3 implementation is present locally. Final PASS evidence and exact command/browser results belong to [VALIDATION](./VALIDATION.md); this document does not invent results before that evidence is recorded.
